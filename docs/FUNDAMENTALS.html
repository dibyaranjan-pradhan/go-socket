Who is who?

Four real-world actors. Four confusing names inside the library. This page separates them so you can explain go-socket to anyone — including yourself before a public release.

1. The four actors in production

End user Human — opens your app in a browser or mobile app. Does not call go-socket directly.
Front-end client Browser / mobile / IoT device — JavaScript, Swift, etc. This is what people mean when they say “the client” in a product sense. It opens WebSocket or sends HTTP to your URLs.
Your Go service Your binary — chat API, dashboard backend, gateway. You write main.go, import go-socket, mount routes, register On("message", ...). This is your product code.
go-socket library github.com/.../go-socket — code you depend on. It is not a separate running process. It runs inside your Go service as a package.

2. Confusing names inside the library

go-socket reuses words that mean something else elsewhere. Use this table:

Word in go-socketWhat people often thinkWhat it actually is
gosocket.Server The whole machine / Kubernetes pod One object in your process that owns handlers, hub, and HTTP handlers. You usually create one per app (or one per feature).
internal.Client The browser app One connected peer — one tab, one phone, one device. Library name for “this socket session on the server side.”
Hub Redis / message broker In-memory registry in your process: who is connected, which rooms they joined, fan-out of emits. Not distributed today.
Transport Truck / network layer How bytes move for one peer: WebSocket (wsTransport) or HTTP polling (pollingTransport).
Handler() Your business handler HTTP handler for WebSocket upgrade — mount on a route like /ws.
EngineIOHandler() Engine.IO server product HTTP handler for polling — mount on /engine.io/. Optional.

3. HTTP polling — who calls what?

Who implements the endpoint?

go-socket implements it. When your service mounts s.EngineIOHandler(), the library’s PollHandler.ServeHTTP runs on each request.

Your Go service only mounts the route — it does not reimplement handshake or long-poll logic.

// YOUR Go service (main.go)
mux.Handle("/engine.io/", s.EngineIOHandler())  // you wire the path
mux.Handle("/ws", s.Handler())                  // WebSocket path

http.ListenAndServe(":8080", mux)             // your process listens

Who calls the HTTP polling API?

The front-end client (or any HTTP client that speaks Engine.IO v4 polling). Not your Go service calling itself.

  • GET /engine.io/?EIO=4&transport=polling — handshake, get sid
  • POST ...&sid=... — send messages to server
  • GET ...&sid=... — long-poll, receive messages from server

Why does that endpoint exist?

WebSocket is not always available. Corporate proxies, old mobile networks, or strict firewalls block long-lived WebSocket connections.

Polling is the fallback: normal HTTP request/response in a loop. Slower and more chatty, but works where WebSocket does not.

Engine.IO shape: many JavaScript clients (Socket.IO ecosystem) expect this handshake + sid + POST/GET pattern. go-socket provides it so those clients can connect without you building that protocol yourself.

If all your clients use raw WebSocket + your JSON wire, you can skip EngineIOHandler() entirely. Polling is optional.

4. WebSocket path (simpler mental model)

Front-end:  new WebSocket("wss://api.example.com/ws")
     ↓
Your service: mux.Handle("/ws", s.Handler())
     ↓
go-socket: upgrade HTTP → wsTransport → internal.Client → Hub
     ↓
Your code:   s.On("hello", func(ctx *Context) { ... })

Same handlers, same rooms, same Emit — whether the peer connected via WebSocket or polling.

Rule of thumb per live connection: about 2 library goroutines (read + write) + shared hub goroutine per gosocket.Server.

10,000 connections (default max) ≈ 20,000 pump goroutines + 1 hub + HTTP workers. That is why MaxConnections exists.

7. Latency — what to expect

TransportTypical latencyWhy
WebSocketLow (ms)Persistent connection; server pushes as soon as WritePump sends
HTTP pollingHigher (up to PongWait / poll timeout)Client must GET and wait; server may hold request until data or ping timeout

Polling is a compatibility path, not a low-latency path. Document that for public users.

8. Scaling — who does what today

What go-socket does today (single process)

  • Hub and rooms live in this process’s RAM
  • EmitToRoom only reaches peers connected to this instance
  • No built-in Redis / NATS bridge yet (roadmap territory)

What your Go service must do to scale horizontally

  • Run multiple replicas behind a load balancer
  • Sticky sessions — same user must hit the same pod (WebSocket and polling sid are local to one instance)
  • Cross-instance broadcast — you add Redis pub/sub, NATS, or similar; on message, publish to other nodes (not in go-socket core today)
  • Tune MaxConnections, HubEmitBufferSize, WriteBufferSize per replica based on load tests

When you need scaling

  • CPU high on broadcast storms → raise HubEmitBufferSize, optimize handlers, shard rooms
  • Memory climbing → check queue depths, message size, connection count
  • Many goroutines → approaching MaxConnections; add replicas with sticky sessions
  • Polling heavy → more HTTP connections and longer-held GETs; need more HTTP timeouts tuning at reverse proxy

9. Engine.IO upgrade (M3 — v0.4.0)

After polling handshake, standard Engine.IO clients can upgrade to WebSocket without a new $connect:

  1. POST 2probe on the polling URL
  2. POST upgrade packet 5
  3. GET transport=websocket&sid=<same sid>

Why it matters: lower latency and fewer HTTP round-trips while keeping Socket.IO client compatibility.

What stays the same: your event handlers, rooms, middleware — only the byte pipe changes via sessionTransport.

Full walkthrough: docs/UPGRADE.md and docs/ARCHITECTURE-VISUAL.html#upgrade-flow.

10. Native WebSocket (alpha)

Config.NativeWebSocket: true switches the WebSocket backend to internal/nativews. Gorilla remains default. Use for Autobahn runs (make autobahn), not production yet.

11. Before public release — honest checklist

  • Document the four actors (this page) so users know what to mount vs what to call
  • State WebSocket is primary; Engine.IO polling is optional fallback
  • Document single-process hub — no multi-node room sync out of the box
  • Publish default limits: MaxConnections 10k, message size 1 MiB, queue depths
  • Recommend load test: N connections, M msg/sec, measure RSS and goroutines
  • Clarify: internal.Client = server-side session for one peer, not your front-end app
