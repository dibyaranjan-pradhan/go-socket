What is go-socket?

go-socket is a real-time communication library that allows Go servers to exchange JSON messages with clients over WebSocket or HTTP long-polling. It provides named events, rooms (broadcast groups), and a middleware pipeline — all without exposing internal complexity to your application code.

WebSocket

Persistent bidirectional connection for real-time messaging

HTTP Polling

Engine.IO v4 fallback for restrictive networks

Zero Dependencies*

Core is std-lib only (*except gorilla/websocket, isolated)

Use Cases

Chat Applications

Real-time message delivery, typing indicators, room-based conversations

Live Dashboards

Push metrics, status updates, and notifications to connected clients

Collaborative Tools

Multi-user editing, presence awareness, synchronized state

IoT Gateways

Device telemetry, command dispatch, real-time monitoring

High-Level Architecture

The Big Picture: Your application talks to Server. The Server manages a Hub which tracks all Clients. Each Client uses a Transport (WebSocket or polling) to talk to the actual network connection. Everything is hidden behind clean interfaces.

WebSocket Connection Flow

When a client connects via WebSocket, here's the exact sequence of events:

1 HTTP Upgrade

Client sends HTTP request with Upgrade: websocket header to server.Handler() endpoint.

GET /ws HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: ...
Sec-WebSocket-Version: 13
↓

2 Server Creates Transport

The WSUpgrader (wrapping gorilla/websocket) performs the handshake and returns a wsTransport that implements the Transport interface.

transport, err := s.upgrader.Upgrade(w, r)
// transport is now a wsTransport wrapping *websocket.Conn
↓

3 Client Object Created

Server creates a Client struct with read/write configuration, generates a random ID, and associates it with the transport.

c := internal.NewClient(hub, transport, ClientOptions{
    ID: randomClientID(),
    MaxMessageSize: cfg.MaxMessageSize,
    WriteWait: cfg.WriteWait,
    PingPeriod: cfg.PingInterval,
    PongWait: cfg.PongWait,
    SendBuffer: cfg.WriteBufferSize,
})
↓

4 Hub Registration

The client is sent to the hub via the hub.Register(c) channel. The hub adds it to the global client map.

↓

5 Middleware Pipeline

Server runs all registered middleware on a synthetic $connect event. If any middleware returns an error, connection is rejected.

connectCtx := s.newContext(ic, r, EventConnect, nil, "", "")
if err := s.runMiddlewares(connectCtx); err != nil {
    // Reject connection
    return
}
↓

6 Start Pumps + OnConnect

Server launches two goroutines:

  • WritePump() — sends outbound messages and periodic pings
  • ReadPump() — reads incoming messages until disconnect

All OnConnect callbacks are invoked (e.g., join room, send welcome).

↓

✓ Connected

Client is now active. Messages flow bidirectionally. Server can emit to this client or broadcast to rooms it joins.

HTTP Polling Connection Flow (Engine.IO)

HTTP long-polling provides a fallback for clients that can't maintain WebSocket connections (proxies, firewalls, mobile background).

1 Handshake GET

Client sends GET /engine.io/?EIO=4&transport=polling (no sid parameter yet).

GET /engine.io/?EIO=4&transport=polling HTTP/1.1

Server response: Engine.IO open packet (type 0) with JSON handshake:

0{"sid":"abc123","pingInterval":25000,"pingTimeout":60000,"maxPayload":1048576,"upgrades":["websocket"]}
↓

2 Session Created

The pollManager creates a session and a pollingTransport. The transport has inbox/outbox channels for bidirectional message passing.

sess := &Session{
    ID: randomSID(),
    PingInterval: 25s,
    PingTimeout: 60s,
    MaxPayload: 1MB,
}
pt := newPollingTransport(sess)
↓

3 Attach Transport

After handshake, server calls s.attachPollTransport(pt, r) which creates a Client with the polling transport and runs the same middleware + pump flow as WebSocket.

↓

4 Client Sends Messages (POST)

Client POSTs messages to /engine.io/?EIO=4&transport=polling&sid=abc123

POST /engine.io/?EIO=4&transport=polling&sid=abc123
Content-Type: text/plain

4{"event":"ping","payload":{}}

The 4 prefix is Engine.IO message packet type. Body is your JSON.

Server unwraps Engine.IO framing → delivers inner JSON to dispatch() → your handler runs.

↓

5 Client Receives Messages (Long-Poll GET)

Client sends GET /engine.io/?EIO=4&transport=polling&sid=abc123 and waits.

Server behavior:

  • If outbound queue has messages, respond immediately with batched packets separated by \x1e
  • If no messages, wait up to PingTimeout
  • If timeout expires with no data, send Engine.IO ping packet (2)
4{"event":"reply","payload":{"ok":1}}\x1e2

↑ Message packet + ping, separated by record separator

↓

✓ Active Session

Client repeatedly POSTs to send and GETs to receive. Server maintains session state in pollManager. Same event handlers and room logic as WebSocket.

Engine.IO Upgrade Flow (M3 — v0.4.0)

What we added: Standard Engine.IO clients can move from HTTP polling to WebSocket on the same session id (sid). Why: Socket.IO ecosystems expect this path; it lowers latency after the initial polling phase. Where: EngineIOHandler() when transport=websocket — see internal/engineio_handler.go and internal/poll_manager.go.

1 Probe (still on polling)

Client POSTs Engine.IO ping with probe payload 2probe. Server marks the session as probed.

POST /engine.io/?EIO=4&transport=polling&sid=abc123
Body: 2probe
↓

2 Upgrade packet

Client POSTs upgrade packet type 5. Server marks session ready for WebSocket GET.

↓

3 WebSocket GET (same sid)

Client opens WebSocket on the Engine.IO URL. Server upgrades HTTP and calls applyUpgrade(sid, wsTransport).

GET /engine.io/?EIO=4&transport=websocket&sid=abc123
Upgrade: websocket
↓

4 Transport swap (no reconnect)

Why sessionTransport exists: The Client read/write pumps keep running. sessionTransport.Swap() replaces polling with eioWebSocketTransport (Engine.IO packets inside WS frames). Polling read returns errTransportUpgraded instead of EOF so pumps do not disconnect.

↓

✓ Same handlers, lower latency

Your On / Emit / room logic unchanged. Hub registration and client ID preserved. Messages now flow over WebSocket text frames wrapped in Engine.IO packet types.

Bug we fixed in M3: An early implementation closed the polling inbox on upgrade, which made ReadPump see EOF and drop the connection (ActiveConnections went to zero). The signal-and-swap pattern avoids that.

Native RFC 6455 Codec (M3 — alpha)

What: internal/nativews — go-socket's in-tree WebSocket server codec (RFC 6455). Why: Isolate gorilla/websocket so we can validate with Autobahn and eventually remove the dependency. How to enable: Config{NativeWebSocket: true} — gorilla remains the default production path.

Default (gorilla)

  • Handler() and Engine.IO WS upgrade
  • Battle-tested; use in production

NativeWebSocket: true

  • TransportUpgrader → nativeTransport
  • Run make autobahn to fuzz the codec
  • Alpha — not for production yet

Direct Handler() WebSocket still carries plain go-socket JSON. Only the Engine.IO mount wraps payloads in Engine.IO packet prefixes.

Key Concepts Explained

Transport Interface

Why it exists: To abstract WebSocket and polling behind a common API so Client pumps don't need to know which they're using.

type Transport interface {
    Name() string
    SetReadLimit(int64)
    SetReadDeadline(time.Time) error
    SetWriteDeadline(time.Time) error
    OnPong(handler func())
    Read() ([]byte, error)
    Write(data []byte) error
    Ping() error
    SendClose() error
    Close() error
}
  • wsTransport wraps *websocket.Conn (gorilla)
  • pollingTransport wraps Engine.IO session channels

Client Read/Write Pumps

ReadPump: Runs in a goroutine, reads messages from transport until EOF or error. On each read:

  • Resets read deadline (heartbeat tracking)
  • Calls onMessage callback → server dispatches to handler
  • On timeout after multiple missed pongs → calls OnHeartbeatTimeout

WritePump: Runs in a goroutine, sends messages from the send channel and periodic pings:

  • Waits on select for outbound message or ping ticker
  • Writes to transport with write deadline
  • On channel close or write error, exits and sends close frame

Hub: The Connection Manager

The hub is a single goroutine running Hub.Run(ctx) that processes channel operations:

Channel Purpose
register Add client to global map
unregister Remove client, clean up rooms
join Add client to room membership
leave Remove client from room
emit Fan-out message to room/client(s)
Why channels? Avoids locking. All state mutations happen in one goroutine. Other goroutines send requests via channels.

Rooms

A room is just a string identifier. The hub maintains:

rooms map[string]map[*Client]struct{}

When you call ctx.JoinRoom("lobby"), the hub adds your client to rooms["lobby"].

When you call ctx.EmitToRoom("lobby", "msg", data), the server sends an EmitJob to the hub, which loops over rooms["lobby"] and calls TrySend on each client.

Broadcast: All clients in room 
ctx.BroadcastToRoom("lobby", "msg", data)
// Excludes sender
Emit: All clients in room 
ctx.EmitToRoom("lobby", "msg", data)
// Includes sender

Middleware Pipeline

Middleware runs before event handlers. It can:

  • Log events (LoggerMiddleware)
  • Recover from panics (Recover)
  • Rate-limit (RateLimiter)
  • Authenticate, authorize, validate
  • Return ErrRejected to block the event
type Middleware interface {
    RunMiddleware(*Context) error
}

s.Use(s.LoggerMiddleware())
s.Use(Recover())
s.Use(CustomAuthMiddleware)

Step-by-Step Breakdown

1 Client Sends

Browser WebSocket API sends JSON text frame.

2 Transport Read

wsTransport.Read() calls conn.ReadMessage(), returns payload bytes.

3 ReadPump Callback

ReadPump calls c.onMessage(data) which is wired to server.dispatch().

4 Server Unmarshal

Server unmarshals JSON into ClientWireMessage{Event, Payload, Room, ID}.

5 Middleware Run

All middleware execute in order. If any returns error, event is rejected.

6 Handler Lookup

Server looks up handlers["ping"], invokes with Context.

7 Handler Emits

Handler calls ctx.Emit("pong", data) → server marshals response.

8 Send to Client

client.TrySend(json) → message goes to send channel.

9 WritePump Receives

WritePump select receives from channel, calls transport.Write().

10 Transport Write

wsTransport.Write() calls conn.WriteMessage(TextMessage, data).

Design Patterns Used

1. Adapter Pattern

Where: Transport interface

Why: Adapts gorilla WebSocket and custom polling logic to a common API so Client doesn't care which it uses.

wsTransport wraps *websocket.Conn
pollingTransport wraps Engine.IO session

2. Channel-Based Concurrency

Where: Hub operations

Why: Avoids locks by funneling all state mutations through channels to a single goroutine.

hub.Register(c)   // → register chan
hub.Join(c, room) // → join chan
hub.Emit(job)     // → emit chan

3. Fan-Out Pattern

Where: Room broadcasts

Why: One emit job fans out to all clients in a room without blocking sender.

for client := range room {
    client.TrySend(data)
}

4. Middleware Chain

Where: Event processing

Why: Cross-cutting concerns (logging, auth, rate-limit) don't pollute business handlers.

s.Use(LoggerMiddleware())
s.Use(Recover())
s.Use(CustomAuth)

5. Pump Goroutines

Where: ReadPump and WritePump

Why: Decouples reading (blocking I/O) from writing (channel-driven) so they don't block each other.

6. Context Object

Where: Context passed to handlers

Why: Encapsulates request data, client ref, helpers (Emit, JoinRoom) in one struct.

ctx.ClientID()
ctx.Emit("reply", data)
ctx.JoinRoom("lobby")

Quick Reference: Common Questions

How do I send a message to all clients in a room? 
ctx.EmitToRoom("lobby", "announcement", map[string]string{
    "message": "Server maintenance in 5 minutes",
})
How do I join a client to a room? 
s.OnConnect(func(ctx *Context) {
    roomID := extractRoomFromURL(ctx.Request())
    ctx.JoinRoom(roomID)
})
What's the difference between EmitToRoom and BroadcastToRoom?

EmitToRoom sends to all clients in the room, including sender.

BroadcastToRoom excludes the sender (useful for "user X is typing" messages).

How do I reject a connection based on auth? 
s.Use(MiddlewareFunc(func(ctx *Context) error {
    if ctx.Event() == EventConnect {
        token := ctx.Request().URL.Query().Get("token")
        if !validateToken(token) {
            return ErrRejected // connection rejected
        }
    }
    return nil
}))
How does Engine.IO polling work vs WebSocket?

WebSocket: Single persistent connection. Messages flow bidirectionally over one socket.

Polling: Client repeatedly GETs (to receive) and POSTs (to send). Server wraps JSON in Engine.IO packet frames (4{"event":"..."}). From your handler's perspective, both look identical — same events, same rooms, same API.

What happens if a client's send buffer fills up?

TrySend uses a non-blocking channel send. If the buffer is full, it logs a warning and calls Shutdown() on that client to avoid blocking the hub.

if !client.TrySend(data) {
    log.Printf("send buffer full, disconnecting client")
    go client.Shutdown()
}
